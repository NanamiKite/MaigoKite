# MaigoKite 交付路线与状态

> 最后更新：2026-10-26。
> 这份路线图说明项目现在能做什么、还缺什么，以及接下来先做什么。功能要求见 [需求与验收](../requirements/RequirementList.md)，具体测试记录可在下方展开查看。

## 1. 排序原则

先让一个实际任务从发起到完成都能正常工作，再增加功能。尽量复用成熟实现，把开发时间用于个人任务体验、权限交互、工作区和桌面安装。

```text
通用执行闭环 → 日常可靠性与手机远程 → 经验证的个人工作流 → 扩展分发与多设备体验
```

团队成员、角色管理、PostgreSQL 团队部署、分布式执行和多人协作不进入当前路线。保留既有工作区/主体字段兼容，不因精简文档删除业务数据边界。

## 2. 核心能力状态

### 当前验收状态

聊天、文件操作、审批、浏览器、只读子 Agent、手工记忆和图片生成已有本机任务测试，但项目还不是稳定版。真实模型服务、Windows 和独立安装包仍未充分验证，安全审查模型也有已知错误。

最近的核心调整已将会话管理、工具权限检查、扩展目录和事件显示整理到各自模块，执行仍由 LangGraph 负责，没有新增一套运行时。10 月 18 日又接入了会话标题来源、独立安全决策标识和可翻译错误码。这些改动有静态检查记录，尚无后续行为回归结果，不能沿用旧测试宣布通过。

桌面依赖已升级为 Electron 44.8.0 / electron-builder 26.17.0。背景、会话标签和正文调宽有 10 月 16 日的定向测试记录；后续图形加速开关、变更抽屉自动刷新、公共网页会话授权及 Electron 升级仍需重新测试。长会话曾测到 127ms 长任务，性能问题尚未关闭。

天线扩展已能按明确目标搜索尺寸、复核两档网格、补画并导出候选包，也能准备新频点/材料/架设输入、计算理想匹配和复核固定元件。Linux 的真实 MCP、生产 Core 审批、取消清理、重启取回与结果导入已有定向记录；自然语言选工具、完整 GUI、Windows 和运行中强杀恢复仍未验收。这项扩展不改变个人通用 Agent 的定位，边界见 [天线工作流](../design/AntennaWorkflow.md)。

OB11 案例的最新候选在三个中心频点和三组网格上达到已选增益/F/B 目标，但尚未证明连续带宽、网格收敛或实物性能。邻频诊断仍有不足，固定理想匹配在 21.3 MHz 的 SWR 约为 8.19。不能据此宣布设计可直接制作，或将一次案例结果推广到所有天线。操作方式见 [独立包说明](../../extensions/antenna_design/README.md)，测试范围在下方单独记录。

SVG 预览和模型目录 TLS 修复已有针对性测试，TLS 修复后尚无完整测试重跑记录。[个人 Agent 行为评测](../testing/AgentEvals.md) 已有 10 项任务及参考脚本验证，但尚未运行真实模型。下方保留的测试数字均属于各自记录日期，不是当前版本的全量通过结论。

## 3. 日常可靠性与手机远程

先解决上面的问题，让已有功能能够稳定处理日常任务，再继续增加能力。

手机远程的优先级是 P1，目前还没有设备配对或移动客户端。按 [手机远程访问](../design/RemoteAccess.md) 的 R0–R3 顺序，先保证本机运行可靠，再完成私有连接、配对、手机任务与审批，最后验证手机断线后的恢复。手机仍使用电脑上的运行时，不另建一套，也不必先完成记忆、工作流或团队系统。

其他候选按依赖和实际需求推进：

- 安全续跑、受控重试、并发预算和超时。
- 登录态托管、历史检索、后台任务与必要通知。
- 扩展健康管理和热重载。
- 在已通过的双开关/遗忘/checkpoint 隔离基础上，补记忆多目录、修改/续接、超预算与 GUI 验收；自动提取和语义检索仍未实现。
- 模型能力/路由/降级、向量嵌入/索引和 OCR 仍需验证需求与完整 API/执行闭环。图片输入及 Images/Responses 生图已进入第五批并有定向回执，不再列为尚未开始的候选；后续只补真实服务、平台和生命周期缺口。

## 4. 个人工作流与扩展生态

| 候选 | 准入条件 |
|---|---|
| 复用成功任务 | 先用声明式技能；确有确定性暂停/恢复需求才组合现有 LangGraph 状态/检查点 |
| 子任务/子智能体扩展 | 现有单层只读委派已定向通过；后台、写入、递归或跨进程扩展前，仍须证明收益，并明确隔离、预算、取消与汇总 |
| 技能包管理、可信分发 | 用户有实际安装/更新需求，再确定版本、摘要值、签名、权限预览和回滚 |
| MCP 多传输 | 先明确认证、凭证与网络信任边界 |
| 天线设计工作流 | 项目求解准入、参数优化、网格复核、理想匹配和候选包已有实现及定向运行；后续补自然语言交互、模型预算、平台测试与工程验证，不重建通用 Runtime |
| 研究、内容、设备辅助、开发、招聘等 | 需求频率、失败成本、节省时间和人工接管证据 |
| 原生手机 App、系统推送、低配置连接 | 首版远程使用反馈后确定 |
| 数据导出、备份和可携带性 | 明确格式、一致性和恢复演练 |

现有只读子 Agent 和天线计算扩展只是各自有限的入口，不代表通用工作流平台已经完成。后续仍按具体需求决定先做哪项、做到什么程度，不预设要自研工作流引擎、插件框架、事件溯源或分布式调度。

## 5. 如何更新这份路线图

- 新增或修改功能后，一起更新当前状态、阶段计划和剩余问题。更新日志说明“改了什么”，这里说明“现在能做什么”，不能只改其中一份。
- 测试完成后更新相应功能的状态。具体版本、命令和结果放在详细测试记录里；只写代码或改文档，不算测试通过，过去通过也不保证后续修改没有问题。
- 保留历史结果，包括失败和跳过，但折叠展示，避免读者把旧状态当成现状。不另建重复的完成度报告。
- 未实现的页面可以提前提供只读说明，不能保存实际无效的配置，也不能算功能完成。
- 真实服务通过才记为 LIVE PASS；本机 HTTP/SSE 模拟服务只验证协议，未运行记为 UNVERIFIED。判断方法见 [测试与验收](../testing/TestPlan.md)，发布要求见 [构建与发布指南](../deployment/ReleaseGuide.md)。
- 正式版本的变化写入 [更新日志](Changelog.md)，不要把这里的计划直接写成发布说明。
